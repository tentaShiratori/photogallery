# 書き方

## ユースケース

1 つの UC は、ユーザーまたはスクリプトが 1 回で果たす目的にする。名前は動詞で終える。主アクターはユーザー、アドミン、スクリプトのいずれか 1 つ。画面を見る UC はユーザー。アップロードはスクリプト。

目的ではない決め方や約束は UC にしない。ルールとして書き、UC から ID で参照する。

必須の項目は、ID、名前、主アクター、事前条件、事後条件（成功）、事後条件（失敗）、フロー。ID は `UC-番号` で、見出しと同じ。欠番は付けない。ファイルは `docs/spec` 直下に 1 UC につき 1 件。ファイル名は `UC-番号-名前.md`。事前条件は、始まるときに既に成り立っていること。無ければ「なし」。失敗の道が無ければ、事後条件（失敗）は「なし」。

フローは 1 から番号を付ける。1 行は主語 1 つと動作 1 つ。主語は主アクターか、ブラウザか、スクリプト。画面の部品は主語にしない。フローには変化だけを書く。直前の手順が行った変化を言い換えただけの行は書かない。道の終わりに残る状態は事後条件に書く。

代替は、分かれた手順の直下に `- 3a.` と書く。次の代替は `- 3b.`。例外は `- 3e.`、次は `- 3f.`。その道の手順はさらに一段下げる。番号で別の手順へ戻るとは書かない。続く変化は、その道の中に書く。

事後条件は、その道の最後に残る変化だけを書く。フローの途中で消えるものは、フローに書く。

画面を見れば分かる並びや位置は書かない。別の条件から逆に分かることは書かない。ブラウザや動画の初期の挙動は書かない。実装、ファイル名、理由は書かない。

画面とコンソールの文言は「」で囲み、今の文字列のまま書く。用語は GLOSSARY.md の語を使う。

空でないときだけ足す項目は、トリガー、関連、未決。

```markdown
## UC-01 ギャラリーを見る

- ID: UC-01
- 名前: ギャラリーを見る
- 主アクター: ユーザー
- 事前条件: なし
- 関連: 年は R-MEDIA-02。順番は R-GAL-01。
- 事後条件（成功）:
- 事後条件（失敗）:

### フロー

1. ユーザーがギャラリーを開く。
   - 1a. 別の成功する道。
     1. ブラウザはその変化を行う。
   - 1e. 目的が達しない道。
     1. ブラウザは失敗の変化を行う。
2. ブラウザは成功の変化を行う。
```

## ルール

ルールは 2 種類ある。

- モデルのルール: 画面や API が無くても成り立つこと。`docs/spec/domain` に置く。
- アプリのルール: 画面や API の振る舞い。`docs/spec/app` に置く。

ファイルはエンティティや集約ごと。1 ファイルに複数のルールを入れてよい。複数の集約にまたがるルールは、主な操作対象を 1 つ決めてそのファイルに書く。サブの対象からは参照する。

各ルールには ID と短い名前を付ける。中身は例を付けた箇条書きにする。フローは持たせない。
